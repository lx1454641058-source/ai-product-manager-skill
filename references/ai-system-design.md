# AI 系统详细设计与参数检查清单

本文件把 AI 基础原理转化为项目分析时可执行的设计检查项。每次分析项目都要逐项判断；不适用的项目项明确写出“不适用”及原因。这里的数值是缺少项目数据时的推荐起点，不是固定标准，必须用真实测试集、流量、SLA、风险等级和成本预算校准。

## 1. 分析输出规则

每个关键设计项同时给出：

- 当前结论与证据类型；
- 推荐方案和备选方案；
- 推荐默认起点；
- 适用与不适用条件；
- 主要失败方式；
- 验证指标与测试方法；
- 需要用户决定的取舍；
- 停止、降级或回滚条件。

不要把“使用某模型、向量库或 Agent”当成方案完成。必须说明各组件负责什么、不负责什么，以及组件之间如何传递数据、权限、状态和错误。

## 2. 系统职责边界

先画出以下责任链：

```text
用户与业务规则
→ 输入与权限
→ 数据/知识来源
→ 检索或工具
→ 模型理解与生成
→ 输出校验
→ 人工确认或自动执行
→ 审计、反馈与改进
```

分别判断：

- 规则系统：处理确定、可解释、必须一致的业务条件。
- 搜索与 RAG：提供最新、可引用的外部事实。
- 模型：理解自然语言、提取、分类、总结、生成和低风险推理。
- 工具：读取或改变外部系统状态。
- Agent：在约束下选择步骤和调用工具。
- 人工：处理高风险决定、例外、冲突、低置信度和责任承担。

任何最终方案都要避免把知识更新、权限判断、精确计算和最终业务责任全部交给模型。

## 3. 数据源与知识库治理

### 3.1 数据源清单

对每类数据记录：

- 数据源名称、业务负责人和技术负责人；
- 原始位置、格式、语言和规模；
- 权威等级与是否为正式依据；
- 创建时间、生效时间、失效时间和版本；
- 更新频率与同步时限；
- 适用部门、地区、角色和用户群；
- 数据分类、敏感等级和访问权限；
- 保存期限、删除要求和审计要求；
- 是否允许发送给第三方模型或服务商；
- 质量问题、缺失字段和冲突来源。

没有明确负责人、版本或有效期的资料不得直接作为高风险回答的唯一依据。

### 3.2 入库流水线

至少设计以下步骤：

```text
发现/上传
→ 病毒与类型检查
→ 权限确认
→ 解析/OCR/转写
→ 结构还原
→ 清洗与去重
→ 质量检查
→ 切分
→ 元数据生成
→ Embedding
→ 索引
→ 抽样验收
→ 发布
```

需要定义：失败重试、失败队列、人工修复、重新入库、删除传播、版本替换和缓存失效。解析失败或关键字段缺失的资料进入隔离区，不应悄悄发布。

### 3.3 文档解析

按格式检查：

- PDF：可搜索文本还是扫描件，页码、标题、脚注、页眉页脚是否保留。
- Word/网页：标题层级、列表、链接、批注和修订是否处理。
- 表格：行列、合并单元格、单位、公式和表头是否保留。
- 图片：清晰度、旋转、裁切、OCR 置信度和原图引用。
- 音频/视频：说话人、转写、时间戳、关键帧和原始证据。

金额、日期、编号、否定词、例外条款和审批条件属于关键字段，应做规则校验或人工抽查。

### 3.4 版本、更新与删除

- 每个文档保存唯一文档 ID、版本 ID、有效期和状态。
- 新版本发布时，旧版本应停止默认召回，但保留审计需要的历史记录。
- 删除必须传播到原文、切分片段、向量、缓存、搜索索引和备份策略。
- 更新后触发增量重建、抽样检索测试和缓存失效。
- 对法规、价格、制度等时效性资料设置过期告警。
- 冲突资料要有权威等级和冲突处理流程，不能交给模型自行猜测。

## 4. 文档切分设计

优先按语义边界切分：标题、章节、条款、段落、问答对、表格或时间段；固定长度只是兜底。

推荐初始实验范围：

- 一般政策、说明和知识文章：每片约 300—800 Token。
- 重叠：约 10%—20%，仅用于避免边界信息丢失。
- 初始对比实验：短、中、长三档，例如 250、500、900 Token。
- 表格、合同条款、流程和代码：按完整结构切分，不机械套用长度。
- 使用父子切分时，小片段负责召回，父章节负责提供完整上下文。

这些只是起点。最终依据召回率、引用准确性、上下文噪声、延迟和成本选择。不要只因为“召回结果看起来不错”就确定切分参数。

每个片段至少携带：文档 ID、片段 ID、标题路径、页码或时间戳、版本、有效期、权限、来源链接、语言、内容类型和校验摘要。

## 5. Embedding 与向量库设计

### 5.1 Embedding 模型选择

检查：

- 是否覆盖项目语言、专业术语和长文本；
- 向量维度、最大输入和单价；
- 相似度效果与批量吞吐；
- 模型版本是否固定并记录；
- 查询与文档是否使用兼容的 Embedding；
- 更换模型时如何双写、重建索引和回滚。

不要把不同维度或不兼容模型生成的向量混在同一索引中。原始文本与元数据必须保留，确保可重新生成向量。

### 5.2 向量库数据模型

至少保存：

- tenant_id：租户或组织隔离；
- document_id、chunk_id、parent_id；
- embedding 与 embedding_version；
- 原始片段或可访问的原文位置；
- 标题路径、页码、时间戳；
- 文档版本、生效与失效时间；
- 部门、地区、角色和 ACL；
- 内容类型、语言和敏感等级；
- 创建、更新时间、删除状态和校验值。

多租户系统优先使用物理或逻辑命名空间隔离，并在检索前执行权限过滤；不能只在模型生成回答后再过滤。

### 5.3 向量库选型检查

比较：

- 数据规模与增长速度；
- 查询延迟、并发和写入吞吐；
- 元数据过滤能力；
- 关键词、向量和混合搜索能力；
- 索引构建、增量更新与删除一致性；
- 多租户隔离、加密、备份和灾难恢复；
- 可观测性、地域部署和合规；
- 运维复杂度、供应商锁定和总成本。

没有真实规模和性能目标时，不直接指定某个数据库品牌。先定义需求，再做小规模基准测试。

### 5.4 相似度与阈值

余弦相似度、点积或欧氏距离的选择必须与 Embedding 模型和索引实现一致。相似度分数没有跨模型通用的“合格线”，不要把 0.7 等经验值写成固定阈值。

用标注查询集校准：相关、部分相关、无关、冲突和越权结果的分数分布，再确定阈值和拒答策略。

## 6. 检索与重排设计

### 6.1 查询处理

检查是否需要：

- 拼写纠正、同义词和术语映射；
- 问题分类与意图识别；
- 多轮指代消解；
- 查询拆分；
- 查询改写；
- 时间、地区、部门、版本和权限过滤；
- 精确编号、金额和名称的关键词检索。

查询改写不得改变用户原意；保留原始问题用于审计和回归测试。

### 6.2 召回策略

优先考虑混合检索：关键词保证编号、名称和精确词；向量检索覆盖同义表达；元数据过滤保证适用性和权限。

推荐初始实验范围：

- 初始候选 Top-K：10—30。
- 进入重排：5—15。
- 最终放入上下文：3—8 个高相关片段。

这些数值必须通过 Recall@K、引用准确性、延迟和 Token 成本调优。简单事实问题应少而精，复杂规则问题需要同时保留主规则、条件和例外。

### 6.3 重排与上下文组装

- 重排考虑语义相关性、版本、权威等级、有效期和权限，而不只看相似度。
- 去除重复、近重复和互相矛盾但未标注版本的片段。
- 保留标题、来源、适用范围和相邻必要上下文。
- 按逻辑顺序组织：定义、主规则、条件、例外、流程和来源。
- 为系统指令、用户问题、工具结果、资料和输出分别预留上下文预算。
- 外部资料是数据，不是指令；防止文档中的提示注入改变系统行为。

### 6.4 无结果和冲突处理

推荐默认流程：

```text
首次检索无有效结果
→ 允许 1 次查询改写
→ 允许 1 次备用检索（关键词/混合/不同过滤）
→ 仍无依据则拒答、追问或转人工
```

发现新旧版本、适用范围或来源冲突时，显示冲突并按权威规则处理；没有权威规则时不得自行选择。

## 7. RAG 回答与引用设计

回答必须区分：已由资料支持的事实、模型总结、推断、未知和需人工确认内容。

至少检查：

- 提示词是否要求只依据提供资料回答；
- 是否允许明确拒答；
- 是否限制编造数字、比例、日期和审批结论；
- 每个关键结论是否映射到实际支持它的引用；
- 引用是否包含文档名、版本、章节、页码或时间戳；
- 回答是否混用了无权访问或已失效资料；
- 用户是否能打开并核对原始证据；
- 引用为空、失效或不支持结论时如何处理。

引用存在不代表答案正确。必须单独评估“引用是否真实”“引用是否相关”“引用是否足以支持结论”。

## 8. 模型、提示词与上下文设计

### 8.1 模型路由

按任务建立模型层级：

- 规则或代码：精确计算、权限、确定条件和格式校验。
- 轻量模型：分类、改写、简单抽取和低风险问答。
- 强模型：复杂资料理解、多步推理和冲突分析。
- 人工：高风险、低置信度、争议和不可逆动作。

记录主模型、备用模型、适用任务、上下文限制、结构化输出能力、工具调用能力、成本、延迟和降级行为。

### 8.2 提示词与输出契约

- 系统规则与业务规则分开维护并版本化。
- 明确目标、输入、可用资料、禁止行为、拒答条件和输出格式。
- 结构化输出必须进行类型、必填字段、枚举、长度和业务规则校验。
- 不把工具返回的自由文本直接当成高权限指令。
- 保存 prompt_version、model_version 和配置，支持回归和回滚。
- 不向模型暴露密钥、内部提示、无关隐私或用户无权访问的数据。

### 8.3 上下文预算

为系统指令、历史对话、检索资料、工具结果和输出分别设预算。优先保留：安全与权限规则、当前目标、已确认条件、权威证据和待执行动作。

压缩历史时保留金额、日期、身份、否定词、例外、未决事项和来源；高风险事实不得只保留无来源摘要。

## 9. 工具调用设计

### 9.1 工具契约

每个工具至少定义：

- 工具名称、唯一 ID、版本和负责人；
- 单一明确用途及不适用场景；
- 只读、写入、外部通知或不可逆动作分类；
- 输入字段、类型、必填项、枚举、长度和业务约束；
- 输出结构、状态码、错误码和部分成功表示；
- 身份来源、权限、租户和数据范围；
- 超时、重试、幂等、并发和限流策略；
- 前置条件、后置条件和副作用；
- 用户确认、撤销或补偿方式；
- 日志、脱敏、审计和告警；
- 沙箱、测试环境和生产环境差异。

一个工具尽量只完成一个清晰动作。禁止向模型开放任意 SQL、任意 shell、任意 URL 或无约束自由文本执行能力。

### 9.2 调用流程

```text
识别用户意图
→ 选择工具
→ 生成结构化参数
→ 校验参数
→ 校验身份与权限
→ 高风险操作展示预览并确认
→ 执行工具
→ 验证真实结果
→ 更新任务状态
→ 记录审计
```

模型声称“已完成”不能作为成功依据，必须读取工具的明确成功结果或再次查询系统状态。

### 9.3 幂等与重复执行

幂等是相同请求重复执行时不会产生额外副作用的性质。支付、提交、创建、退款、发信和删除等写操作应使用幂等键、业务唯一键或状态机保护。

- 同一逻辑动作的重试使用同一个幂等键。
- 工具超时后先查询状态，再决定是否重试。
- 结果未知时不生成新的业务请求 ID。
- 无法保证幂等的写操作不自动重试，转人工或要求用户确认。
- 重复提交、重复通知和重复扣款必须有监控和补偿流程。

## 10. 超时、重试与故障恢复

### 10.1 基本原则

- 重试只处理暂时性错误，不修复参数、权限、业务规则或数据错误。
- 每次请求有总截止时间；单个重试不能超过剩余预算。
- 使用指数退避和随机抖动，避免大量客户端同时重试。
- 遵守服务端 `Retry-After`。
- 记录首次调用与每次重试，不把重试后的成功掩盖为无故障。
- 达到上限后停止，选择拒答、排队、降级、回滚或人工接管。

### 10.2 推荐默认起点

| 场景 | 默认起点 | 处理方式 | 停止条件 |
|---|---|---|---|
| 只读查询遇到网络错误、408、502、503、504 | 首次调用 + 最多 2 次重试，共 3 次总尝试 | 指数退避加抖动；每次前检查剩余时间 | 达到 3 次、总截止时间耗尽或错误变为非暂时性 |
| 429 限流 | 最多 2 次重试 | 优先遵守 Retry-After；否则排队或降级 | 超过用户等待预算或持续限流 |
| 身份令牌过期 | 刷新 1 次并重放 1 次 | 刷新失败立即停止 | 第二次仍为认证错误 |
| 参数格式错误或模型生成了无效参数 | 允许模型修复 1 次 | 返回明确字段错误，不自由猜测缺失业务数据 | 修复后仍不合法 |
| 权限拒绝、业务规则拒绝、普通 4xx | 0 次自动重试 | 提示原因、补充条件或申请权限 | 立即停止 |
| 幂等写操作超时或结果未知 | 先查状态，必要时最多 1 次受控重试 | 使用同一幂等键；验证最终状态 | 状态仍未知或重复风险不可接受 |
| 非幂等写操作超时或结果未知 | 0 次自动重试 | 查询状态、人工接管或用户确认 | 不自动重复执行 |
| 检索无结果 | 1 次查询改写 + 1 次备用检索 | 保留原问题，记录改写和过滤变化 | 仍无有效依据则拒答/追问/转人工 |
| OCR/语音低置信度 | 最多 1 次重新处理 | 调整旋转、降噪、语言或识别方式 | 仍低置信度则人工确认原始证据 |
| 工具返回无法解析的结果 | 1 次格式修复或备用解析 | 不把损坏结果交给下游写操作 | 第二次失败停止 |

“2 次重试”不等于所有场景都应重试两次。交互式低延迟任务可能只允许 1 次；离线任务可以排队，但必须有总次数和总时长上限。

### 10.3 Agent 步数和循环

推荐初始起点：

- 简单任务最大 4—6 个步骤；复杂任务最大 8—12 个步骤。
- 同一工具使用相同参数连续调用 2 次仍无新状态时停止。
- 同一错误连续出现 2 次时停止自动修复。
- 每个任务同时设置步骤、工具调用、Token、成本和总时长预算。
- 接近预算时先保存状态，再降级、追问或转人工。

步骤上限必须按任务拆解和测试调整，不能用提高上限掩盖规划错误。

### 10.4 熔断与降级

熔断是在依赖服务持续失败时暂时停止调用，防止故障扩散。根据流量使用连续失败数或时间窗口错误率触发，阈值应通过正常基线校准。

降级顺序示例：

```text
强模型 → 轻量模型
生成回答 → 仅返回权威资料
实时处理 → 排队异步处理
自动执行 → 生成草稿并人工确认
外部服务 → 备用服务或人工流程
```

高风险场景不得通过降级跳过权限、引用、核验或人工确认。

## 11. Agent 工作流与记忆

- 高风险流程优先使用确定性状态机；模型负责理解和低风险分支。
- 明确每个状态的进入条件、允许工具、退出条件、超时和补偿动作。
- 区分对话上下文、当前任务状态、用户偏好和长期业务知识。
- 长期记忆需要用户授权、来源、更新时间、过期时间、编辑和删除能力。
- 任务状态保存已完成步骤、待完成步骤、证据、工具结果和未决问题。
- 不把模型生成的推测写成用户事实或长期记忆。
- 多 Agent 系统要定义负责人、共享状态、交接格式、冲突处理、总预算和最终决策者。

## 12. 多模态处理

对图片、OCR、语音和视频分别记录：输入质量要求、预处理、识别模型、置信度、原始证据、人工核验、保存期限和成本。

- OCR 金额、日期、编号和否定词要规则校验或人工复核。
- 表格需要保持行列和表头关系，不只提取连续文本。
- 语音需要处理口音、噪声、专业词和说话人；关键数字可要求重复确认。
- 视频需要按音频、转写、字幕、关键帧和时间戳分层处理。
- 多模态结果进入知识库时，引用必须能回到原图区域、音频或视频时间点。

## 13. 用户体验与人机协同

至少设计：

- 输入要求、示例和错误提示；
- 加载、检索、生成、工具执行和人工处理状态；
- 引用、版本、适用范围和不确定性展示；
- 追问、编辑、重试、撤销和反馈；
- 自动执行前的动作预览、影响范围和确认；
- 失败后保留进度和可继续入口；
- 无法回答时的合理拒答和人工路径；
- 无障碍、多语言和移动端限制。

不要把模型置信度数字直接当作用户可信度。优先展示依据、缺失信息、冲突和下一步。

## 14. 评估体系

### 14.1 分层评估

分别评估：

- 输入层：OCR、转写、解析和字段提取。
- 检索层：Recall@K、Precision@K、MRR/nDCG、版本正确率、权限违规率。
- 生成层：正确性、相关性、完整性、忠实度、引用一致性和合理拒答。
- 工具层：参数正确率、调用成功率、重复执行率、超时率和恢复率。
- Agent 层：任务完成率、平均步骤数、循环率、人工接管率和不可逆错误率。
- 体验层：首响应时间、完整时间、用户完成率、重试率、投诉和撤销。
- 业务层：真实问题解决率、节省工时、转化或风险损失变化。
- 成本层：单次请求成本、单次有效任务成本、人工审核成本和失败成本。

### 14.2 测试集

测试集至少覆盖：常见、长尾、模糊、信息缺失、边界、冲突、旧版本、无答案、越权、隐私、提示注入、恶意输入、工具失败、重复提交、缓存过期、高并发和降级。

每条测试包含：输入、用户与权限、参考依据、期望行为、禁止行为、严重度、实际结果、错误层级和是否阻止上线。

### 14.3 发布门槛

不要只设平均准确率。单独为高风险错误、权限泄露、错误写入和无依据确定性回答设零容忍或严格上限。门槛必须说明样本量、置信区间、适用人群和测试版本。

## 15. 可观测性、监控与审计

为一次任务生成关联 ID，串联：用户请求、身份、prompt/model 版本、检索查询、召回片段、工具调用、重试、人工确认、输出和反馈。

至少监控：

- 各阶段延迟、Token、成本和错误率；
- 检索空结果、低相关结果、旧版本和权限过滤；
- 工具超时、重试、重复执行和结果未知；
- Agent 步数、循环、预算耗尽和人工接管；
- 幻觉、引用不一致、拒答和严重错误；
- 缓存命中、缓存陈旧和错误跨用户复用；
- 模型、提示词、Embedding、索引和知识版本变化后的质量漂移。

日志必须脱敏，限制访问并设保存期限。审计日志与调试日志可分开管理。

## 16. 安全、隐私与权限

- 数据最小化、目的限制、保存期限、删除和用户授权。
- 传输与存储加密、密钥管理和环境隔离。
- 用户、服务账号和 Agent 使用最小权限。
- 租户、部门、角色和字段级权限在检索与工具执行前生效。
- 防止提示注入、工具注入、数据外泄、越权检索和敏感日志。
- 外部资料、网页和工具返回视为不可信内容。
- 高风险写操作需要可解释预览、明确确认、撤销或补偿和完整审计。
- 供应商、模型和第三方工具要检查数据使用、地域、保存和删除条款。

## 17. 性能、成本与单位经济性

建立端到端预算：

```text
总延迟 = 上传/解析 + 检索 + 重排 + 模型 + 工具 + 校验
总成本 = 模型 + Embedding/检索 + 存储 + 工具 + 人工 + 重试/失败
单次有效任务成本 = 总成本 ÷ 成功解决的任务数
```

分别设置首响应、完整响应、异步任务和高峰期目标。缓存必须包含模型、提示词、知识版本、权限和个性化条件；任一关键条件变化时失效。

成本优化顺序通常是：减少无效调用、缩短无关上下文、复用安全缓存、按任务路由模型、批处理离线任务、最后才是牺牲质量。高风险任务不能为了降本省略核验。

## 18. 上线、变更与回滚

- 先离线评估，再内部测试、影子运行、受限试点和逐步放量。
- 写操作先使用只读或草稿模式，确认可靠后再开放执行。
- 模型、提示词、Embedding、切分、索引、重排和工具契约的每次变更都要版本化并回归测试。
- 定义灰度范围、上线门槛、监控窗口、暂停条件和一键回滚方案。
- 回滚时考虑模型配置、索引、缓存、数据库状态和已经发生的外部副作用。
- 上线后定期审查知识新鲜度、权限、成本、错误分类和人工负担。

## 19. 完整分析交付物

一次完整项目分析至少产出：

1. 项目简报、问题证据、用户场景和成功标准。
2. AI 适用性与规则/搜索/模型/RAG/Agent/多模态取舍。
3. 系统职责图、正常流程、异常流程和人工接管。
4. 数据源、知识库、入库、版本、权限和删除设计。
5. 切分、Embedding、向量库、检索、重排、上下文和引用设计。
6. 模型路由、提示词、输出契约和上下文预算。
7. 工具目录、工具契约、幂等、超时、重试、补偿和审计。
8. Agent 状态、记忆、步骤预算、终止条件和循环保护。
9. 多模态解析、原始证据、质量和隐私设计。
10. 分层测试集、指标、发布门槛和回归方案。
11. 监控、告警、缓存、限流、降级、成本与单位经济性。
12. MVP、试点、上线、回滚、复盘和需用户决策事项。
