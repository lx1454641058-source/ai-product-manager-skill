# 生命周期计划质量与控制

本文件仅用于已选定的完整生命周期规划或对该计划的质量审核，普通计划表和阶段推进不启用本文件。完整覆盖不等于立即实施全部阶段；企业签核按真实要求，已有授权按原范围复用。未来阶段允许有依据的假设，不虚构批准或团队承诺。

## 1. 34 步覆盖清单

首次完整规划必须逐项覆盖下列 34 个稳定来源步骤，不能把 `L01-01 至 L10-05`误解为每个阶段都有 5 步，也不能只检查首尾编号：

```text
L01-01 L01-02 L01-03
L02-01 L02-02 L02-03
L03-01 L03-02 L03-03
L04-01 L04-02 L04-03
L05-01 L05-02 L05-03
L06-01 L06-02 L06-03
L07-01 L07-02 L07-03
L08-01 L08-02 L08-03 L08-04
L09-01 L09-02 L09-03 L09-04
L10-01 L10-02 L10-03 L10-04 L10-05
```

每个来源步骤必须在详细计划中出现且可追溯。一个步骤可以拆成多个可执行任务；多个步骤可以合并为一项任务，但必须列出全部来源 ID，并解释合并后为什么仍能分别验收。不适用项只保留原因和重新触发条件，不填写无意义的详细卡；只有排除项改变已约定范围或风险控制时才记录批准人及证据。

## 2. 分层呈现，保持同一事实来源

完整计划默认使用三层，而不是把所有内容硬塞进一个超宽表：

1. **执行摘要**：目标、边界、推荐总方案、十阶段状态、关键路径、决策门、最高风险和当前 3—5 个行动。
2. **可跟踪主计划**：任务 ID、来源步骤、责任、依赖、时间窗、交付物、验收、状态、决策门和下一步。
3. **逐步详细卡**：当前判断与证据、推荐方案与理由、动作、DoR/DoD、问题预演、预防、监测、处置、备选与回退。

“分层”只改变展示，不复制状态。摘要、风险表、当前行动和详细卡都必须引用同一任务 ID；同一字段冲突时，以受控主计划的最新版本为准。

完整规划可直接在回答中展开。用户明确要求文件、计划表、可长期推进的产物，或内容长到不利于聊天阅读时，应生成一份 Markdown 或电子表格主计划并在回答中提供摘要；不要因为用户没有指定文件格式而静默省略步骤。选择格式只在会实质影响用户使用方式时询问。

## 3. 候选计划、批准基线与变更

- 首次生成的计划标记为`候选版`，不代表团队已经接受范围、资源、日期或风险。
- 在有权人批准目标、范围、责任、资源和关键门槛后，才标记为`批准基线`并分配版本号，例如 v1.0。
- 变更范围、里程碑、关键门槛、预算、最终负责人或高风险控制时，记录变更 ID、原因、影响任务、旧值、新值、提出人、批准人、日期和回退方案。
- 普通状态和证据更新可以直接更新主计划，但必须保留最后更新时间；不能伪造已经发生的批准、委派或完成。

出现需要跟踪的事项时维护以下关联记录，可合并进同一计划；没有对应事项不建立空台账：

| 台账 | 最低字段 |
|---|---|
| 决策 | 决策 ID、问题、选项、推荐、取舍、有权人、截止、决定与证据 |
| 风险 | 风险 ID、关联任务、触发、影响、概率/严重度、预防、监测、处置、责任人、回退 |
| 问题/阻塞 | 问题 ID、关联任务、当前影响、解除条件、责任人、升级时间、替代路径 |
| 变更 | 变更 ID、关联任务、原因、前后差异、下游影响、批准人、回退、状态 |

## 4. 可开始、可完成与专业签核

每个可执行任务同时定义：

- `DoR`（Definition of Ready）：开始前所需输入、权限、负责人和前置决策；未满足时不得假装进入执行。
- `DoD`（Definition of Done）：交付物、验收证据、质量门槛和签核角色；仅生成文档、召开会议或到达日期不等于完成。
- `执行负责人`：实际完成工作的人或角色。
- `最终负责人`：对结果负责的人或角色，只设一个；不等于所有任务均须其逐项签收。内部任务可按授权由自动检查或 AI 自检关闭，只有约定或风险确需时才要求真人接受记录。
- `专业签核`：只有真实组织、合同或具体风险要求时设置；个人项目可由 AI 承担已授权的分析、实现和自检，但不能把自检冒称独立专业签核。

职能例行职责必须写出“应主动做什么、何时触发、提供什么证据、发现异常如何升级”。不能把所有跨职能工作写成“PM 通知后才开始”，也不能用部门名掩盖责任空缺。

### 4.1 验收条件契约

DoD 说明完成边界，但每个任务还必须把验收拆成可执行的判定契约：

| 字段 | 要回答的问题 | 合格写法示例 |
|---|---|---|
| 验收对象 | 验收哪一个版本、范围、数据或流程 | PRD v1.0 中三类设备的主流程与八类异常流程 |
| 验收条件 | 什么结果算通过 | 所有 Must 需求均有正常、边界和失败用例；无未分配的严重风险 |
| 指标/阈值 | 用什么口径判断 | 100 条冻结样本中高风险漏拦截为 0；普通错误率不高于待批准阈值 |
| 验收方法 | 具体怎样检查 | 文档走查、样本复算、端到端测试、权限测试、演练或真实状态回查 |
| 验收证据 | 留下什么可复核记录 | 测试报告版本、系统日志、签收记录、决策 ID 和证据位置 |
| 验收方式与责任 | 谁或什么检查可判定完成，是否确需人工接受 | 内部文档由 AI 自检，功能由约定测试核验；用户体验或真实专业签核由相应人员确认，不笼统要求每项都由用户签收 |
| 未通过处理 | 失败后回到哪里 | 退回 L05-02 修复并重跑回归；阻断 G3，不进入试点 |

验收条件遵循以下规则：

- 优先使用二元可判定条件，例如“34 个来源 ID 均出现且无重复”，避免“内容较完整”。
- 质量类任务同时写主指标、保护指标、严重错误上限、样本与时间窗口；不能用平均值掩盖高风险失败。
- 数值没有依据时写“候选阈值/待批准”，附验证方法和批准决策门，不能编造精确标准。
- 一个任务可能需要多专业签核；分别说明各自验收范围，但仍保留一个最终负责人决定任务是否关闭。
- 验收发现缺陷时记录问题 ID，写清修复责任人、复验范围和重新进入决策门的条件。
- 验收条件发生变化属于受控变更，必须记录原因和对下游任务、测试及已交付结果的影响。

## 5. 排期、依赖与关键路径

- 人员、容量和外部接口未确认时，使用相对时间窗或范围，标记为假设；不要伪造日历日期。
- 区分硬依赖、可并行、软依赖和外部依赖；依赖必须引用任务 ID 或具名外部条件。
- 识别关键路径：任何延误都会推迟决策门或里程碑的连续任务链。
- 为高不确定性外部依赖提供缓冲、替代方案和最晚切换点。
- 计划开始和完成之外，按需要给出工作量、持续时间、负责人容量、里程碑和沟通节奏；数字均标明证据或假设。

## 6. 逐步方案的最低深度

每个适用来源步骤的详细卡至少回答以下问题；低风险步骤可合并表达，不适用步骤只保留排除理由和重新触发条件：

1. 当前知道什么、证据属于用户输入/公开数据/推算/假设中的哪一种，还有什么未知；
2. 推荐方案是什么，为什么适合当前项目，何时不适用；
3. 按顺序做哪些动作，DoR 和 DoD 是什么；
4. 谁执行、谁最终负责、PM 做什么、哪些职能应主动完成什么；
5. 输入、依赖、交付物、验收对象、验收条件、指标/阈值、验收方法、验收证据、验收人、未通过处理、时间窗和下一步是什么；
6. 最可能且影响最大的失败方式是什么；
7. 事前怎样预防、过程中看什么信号、发生后谁怎样处理；
8. 备选方案、切换条件、暂停/停止/回退和升级条件是什么。

同一个主要问题必须形成完整闭环：`触发/原因 → 预防 → 可观测信号 → 处置动作与责任人 → 恢复验证 → 回退或停止条件`。如果一个步骤有多个独立高风险问题，可以链接中央风险 ID，避免重复长篇描述，但详细卡仍要说明该风险如何影响本步骤。

## 7. 首版计划质量检查

交付前逐项检查：

- 34 个稳定来源 ID 是否全部出现、没有重复遗漏或误造；
- 十阶段后期工作是否因篇幅被省略；
- 每一步是否真正项目化，而非复述通用知识；
- 每个适用步骤是否有推荐、执行、责任、依赖、DoR、DoD，以及可判定的验收对象、条件、方法、证据、验收责任和未通过处理；不适用步骤是否有理由；
- 验收条件是否避免“评审通过、符合预期、效果良好”等没有口径的表述；候选数值是否标记待批准并绑定决策门；
- 所有数字、完成、批准、委派和测试是否有证据标签；
- 候选计划是否被误写成团队承诺；
- 主计划、风险、决策、问题和变更记录是否能通过 ID 互相追溯；
- 是否有责任空缺、外部依赖、关键路径、决策门和当前 3—5 个行动；
- PM 是否替代了专业职能或有权人，或者反过来遗漏了 PM 应做的产品判断；
- 是否给出不使用 AI、降低自动化或停止项目的真实选项；
- 退场计划是否定义必要的转移与演练证据；仅实际进入退场验收时才要求这些证据已经发生。

如果任一关键项缺失，先补齐计划再宣称完成。质量检查验证结构和可执行性，不证明项目结论真实；真实结论仍需调研、测试、签核和运行证据。
