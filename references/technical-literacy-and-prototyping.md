# 技术实现可读性与原型边界检查

本文件用于把 AI 产品方案落到可联调、可验收的技术链路。适用于应用原型、前后端联调、API 集成、文件处理、关系型数据库、身份认证、权限控制和第三方服务。目标是让产品分析能判断数据如何流动、状态如何变化、失败如何处理以及原型证明了什么；按相关链路查阅，不要求每次展开全部章节。用户要求实施时，可在授权和能力范围内完成技术设计、代码与验证；不要将产品经理角色理解为禁止技术执行。

## 1. 先画端到端数据链

至少画出：

```text
用户输入
→ 页面或客户端
→ 输入校验
→ JSON/文件封装
→ HTTP/API
→ 服务端处理
→ 数据库、模型或外部工具
→ 输出校验
→ 页面展示或状态变更
→ 日志、监控与审计
```

对每一步写清输入、输出、数据类型、负责人、权限、状态、错误和是否产生副作用。不要把“页面有结果”“JSON 合法”“接口返回 200”直接等同于业务成功。

## 2. Python 与服务端处理可读性

当原型或服务使用 Python 时，不要求产品经理编写代码，但分析应能识别：

- 变量保存什么业务数据，字符串、整数、小数、布尔值和空值是否混用；
- 列表、字典、元组和集合分别承载多条数据、结构化记录、固定组合或去重集合；
- 条件判断是否覆盖空输入、权限不足、无结果和失败分支；
- 循环批量处理时，空集合、单条失败、大数据量和中途终止如何处理；
- 函数和模块的输入、输出、职责和失败方式是否清晰，接口、文件、权限和数据逻辑是否过度耦合；
- 异常是否被分类处理，还是被统一吞掉并返回模糊“系统错误”；
- 文件的格式、大小、编码、解析、临时存储、访问、保留和删除是否明确；
- 虚拟环境和依赖版本是否可复现，开发、测试和生产环境是否一致。

## 3. JSON 与结构化数据契约

对请求、响应、模型结构化输出和工具参数，检查：

- 对象、数组、字段和嵌套关系；
- 字符串、数字、布尔值、空值、对象和数组类型；
- 必填、可选、默认值、枚举、长度、范围和格式；
- 缺失字段、`null`、空字符串、空数组和零值分别代表什么；
- 序列化与反序列化后，日期、数字、布尔值和字符编码是否保持预期；
- 新增、删除、改名、改类型或改变嵌套层级时的兼容策略；
- API、客户端、数据库和模型输出使用的字段含义是否一致；
- 是否通过版本号、变更说明、兼容窗口和回归测试管理变化。

结构合法只是第一层。继续检查数据是否真实、业务是否允许、权限是否允许、外部动作是否真实成功。

## 4. HTTP 与 API 契约

每个 API 至少记录：

- URL、环境和版本；
- GET、POST、PUT、PATCH、DELETE 等方法及其业务含义；
- 路径参数、查询参数、请求头和请求体；
- 参数名称、类型、必填项、约束和示例；
- 响应字段、状态码、业务错误码、部分成功和结果未知的表达；
- 同步、异步、轮询、Webhook 或流式响应方式；
- 超时、总截止时间、重试、退避、幂等、并发和限流；
- HTTPS、跨域 CORS、日志脱敏和密钥传递；
- API Key、Token 或 OAuth 的身份来源、有效期、刷新、撤销和权限范围；
- 分页的页码/游标、每页数量、总数、排序稳定性和重复/遗漏风险。

错误至少区分：参数错误、未认证、无权限、资源不存在、空数据、冲突、限流、超时、服务错误、依赖失败和结果未知。认证失败或业务拒绝不应盲目重试；写操作超时先查询真实状态，再决定是否使用同一幂等键受控重试。

Webhook 要检查签名验证、重复通知、乱序、延迟、失败重送和接收方幂等。流式响应要检查首段延迟、中断、取消、部分内容保存、最终完成标记和错误后恢复。

## 5. 关系型数据库与持久化

关系型数据设计至少说明：

- 需要哪些表，以及每张表保存什么业务实体；
- 字段名称、类型、必填、默认值、敏感等级和生命周期；
- 主键如何唯一识别记录，外键如何关联用户、文件、会话、问答和任务；
- 一对一、一对多、多对多关系是否符合业务规则；
- Create、Read、Update、Delete 的权限、状态变化和审计要求；
- 删除是软删除还是永久删除，删除是否传播到文件、索引、缓存和备份策略；
- 哪些关联操作需要事务，失败时如何回滚或补偿；
- 高频查询、排序和过滤场景是否需要索引，索引的写入和存储代价是否可接受；
- 多租户、部门、角色和资源所有权是否在查询前过滤；
- 数据迁移、版本变化、备份、恢复和审计记录是否有方案。

产品经理不必编写 SQL，但应能把业务对象映射为表、字段、记录和关系，并指出核心 CRUD、事务一致性和权限边界。

## 6. 身份、权限与凭证

分开检查：

- 身份认证：系统如何确认用户或服务是谁；
- 授权：该身份能访问哪些资源、字段和动作；
- 角色：普通用户、团队管理员、企业管理员和系统管理员的权限边界；
- 数据隔离：个人、团队、企业和租户之间是否在查询、检索、缓存和导出前隔离；
- 凭证：API Key、Token、OAuth 授权码和刷新凭证的存放、有效期、撤销和轮换；
- 最小权限：服务账号、模型和 Agent 只获得完成当前任务所需的权限；
- 审计：管理员查看、导出、修改权限和高风险操作是否可追溯。

“已登录”不代表有权访问所有资源；Prompt 中声明某个角色，也不会产生真实系统权限。

## 7. 异常、状态和重复执行

状态至少区分：未开始、处理中、成功、失败、已取消、部分成功和结果未知。异步任务还应说明进度、查询方式、完成通知和超时后的状态核验。

异常设计检查：

- 空输入、空文件、空查询结果和空模型答案是否被区分；
- 参数、认证、授权、业务规则和系统故障是否给出不同处理；
- 用户是否看到可理解的原因、可执行的下一步和可重试条件；
- 重试是否只针对暂时性错误，并有总次数、总时间和停止条件；
- 重复点击、网络重放、Webhook 重送和客户端刷新是否会重复创建、扣费、发送或删除；
- 事务、幂等键、业务唯一键、状态机或补偿流程是否保护写操作；
- 接口超时后是否先核验状态，避免把“结果未知”错误标记为失败；
- 失败后是否保留必要进度，并提供降级、人工接管或恢复入口。

## 8. Figma、Streamlit、Gradio 与 Mock 的验证边界

先明确当前原型要验证哪一种风险：

| 工具 | 主要验证 | 可以证明 | 不能单独证明 |
|---|---|---|---|
| Figma | 页面、信息架构和交互路径 | 用户是否理解界面与流程 | 真实数据处理、模型质量、接口、权限、性能和成本 |
| Gradio | 模型输入到输出的能力 | 模型或 Prompt 在样例上的基本效果 | 完整业务流程、账号权限、数据治理和生产稳定性 |
| Streamlit | 可运行的数据与业务流程 | 文件、Python、API、模型和页面能否初步串联 | 生产级并发、安全、复杂权限、前端体验和运维能力 |
| Mock | 预设接口与异常场景 | 页面状态、字段契约和错误流程能否按预期表现 | 真实模型效果、真实延迟、费用、权限和外部服务可靠性 |

原型结论必须标注为以下之一：

- 视觉交互已验证；
- 模型能力初步验证；
- 业务链路初步跑通；
- 模拟接口流程已验证；
- 生产条件仍待验证。

不要把 Figma 可点击、Gradio 有输出、Streamlit 能运行或 Mock 返回成功写成“产品已上线”或“系统已具备生产能力”。

## 9. 从原型到生产的门槛

原型转生产前至少补齐：

- 正式账号、角色、权限和数据隔离；
- 数据库、文件存储、备份、恢复、删除和审计；
- API 版本、状态码、兼容、超时、重试、幂等和限流；
- 真实模型、真实文件、真实权限和真实异常的端到端测试；
- 常见、边界、无答案、高风险、恶意输入和失败流程测试集；
- 延迟、并发、容量、单次有效任务成本和高峰降级；
- 密钥管理、HTTPS、CORS、敏感日志和第三方数据条款；
- 监控、告警、人工接管、暂停和回滚方案；
- 真实用户试点及可解释的成功标准。

统一使用三级判断：

1. 原型可用：核心体验或流程可演示；
2. 功能可用：主要场景在真实依赖下稳定完成；
3. 生产可用：质量、权限、安全、性能、成本、监控和运维达到上线标准。

## 10. 推荐分析产物

对涉及上述技术链路的项目，按需要产出：

- 端到端数据流图；
- JSON 字段与类型表；
- API 契约和错误码表；
- 数据表关系图与 CRUD 矩阵；
- 角色—资源—动作权限矩阵；
- 状态机、异常矩阵和重试/幂等检查表；
- Figma、Gradio、Streamlit、Mock 的验证范围表；
- 从原型到生产的差距清单与验收门槛。
