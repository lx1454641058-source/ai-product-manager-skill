# AI 产品项目编排

本文件用于多步骤推进和状态接续。沿用 SKILL.md 选择的任务范围；阶段推进采用精简计划，完整生命周期才使用十阶段、34 步和详细管理字段。

## 1. 一份计划与精简字段

先复用项目已有计划、任务编号和状态名称，不创建平行的总管计划与产品经理计划。无现成记录且需要跨步骤或跨会话接续时，再创建一份可更新的 Markdown 或表格。

最小字段：任务、状态、依赖、交付物、验收依据和下一动作。多角色时增加实际负责人；有预算、时间约束或重要风险时增加对应字段。任务编号用于稳定追踪，不必为一次修改建立十阶段编号体系。

可使用状态：未开始、进行中、待验证、阻塞、已完成、已暂停、已取消。进行中要有实际动作；完成要有符合本次验收的成果；文档完成不等于实施完成。状态更新保留证据和更新时间。

首次阶段计划从当前目标拆出可执行工作，明确真正的前置条件，并在已有授权内推进。允许用合理假设开始可逆验证，不把未来的发布批准作为当前本地准备工作的前置条件。

## 2. 责任与授权

按真实组织安排角色，个人项目默认由当前 AI 完成已授权的分析、实现和自检，不为凑齐部门虚构负责人。确有多人或独立工具任务时再记录执行、协调及复核责任；自己检查不能冒称独立专家签核。

用户保留目标、实质范围、费用和高风险动作的决定权；已有具体授权在原范围继续有效。只有确实需要真人承担的责任或外部权限缺失时标为阻塞。普通实现选择、格式、排序和可逆细节由 AI 在范围内决定。

最终业务负责人不必逐项签收内部任务；在既定验收条件下可由自动检查或 AI 自检关闭任务。需要用户体验、真实责任移交或明确约定的专业验收时才设置人工接受记录，并仅阻断依赖该记录的动作。

企业项目中的专业签核根据真实组织、合同和具体风险确定，记录签核对象、所需角色、证据和影响的阶段；不得将未经签核的建议冒称正式批准。没有独立岗位不等于没有工作执行者，也不等于可绕过真实要求。

## 3. 持续更新

- 先匹配原任务和证据，再更新发生变化的部分，不重读未变手册或重建已完成清单。
- 范围、依赖、负责人或关键门槛变化时，检查受影响的下游任务；无关工作继续。
- 阻塞写清事实、解除条件和可行替代路径；不要因为一个发布步骤缺授权就停止分析、制作和本地检查。
- 用户问状态时报告实际进展，不重新派发、重复外部操作或把历史“运行中”当成当前事实。
- 对话只突出本轮成果、变化、关键阻塞和下一动作。完整表只在用户要求或结构变化需要时展示。

## 4. 完整生命周期规划专用

只有 SKILL.md 定义的完整生命周期请求才使用本节。完整读取 [生命周期手册](lifecycle-playbook.md) 和 [质量控制](plan-quality-and-control.md) 的步骤与覆盖规则，再结合当前项目编制计划。

覆盖十阶段：发现问题、验证机会、设计方案、确定需求与最小可验证产品、构建、评估试点、上线、迭代、移交、退场。阶段允许并行；真实依赖和阶段准入条件决定顺序。

全部 34 个来源 ID 保留可追溯关系。适用步骤落到推荐、动作、责任、依赖、交付、验收、风险和备选；不适用项简述原因及重新触发条件。只有排除项会改变已有约定或风险控制时才需批准，不为普通不适用项新增审批。

详细字段按需分层：

- 主计划：任务 ID、来源步骤、阶段、实际/建议负责人、依赖、时间窗、交付物、验收、状态与下一步。
- 关键任务卡：当前证据、推荐理由、可开始条件（DoR）、可完成条件（DoD）、验收方法和失败处理。
- 风险与变更：仅维护实际需要跟踪的风险、问题、决策与变更记录，可放同一文件；通过任务 ID 关联，不重复长篇内容。
- 真实签核要求：注明谁确认哪一项、批准依据及是否阻断该阶段；未批准的候选计划不能冒称团队承诺。

计划包含未来阶段，不要求未来工作现在完成。无数据的日期或阈值用候选值、相对时间窗及验证方法，不伪造承诺。已有授权覆盖的低风险执行不必等待整个生命周期计划获批。

## 5. 阶段准入与结束

准入条件作用于它实际保护的动作：问题价值不足则重新验证或停止投入；核心链路未跑通则不进入依赖它的试点；质量或安全未达门槛则阻止相应发布。低风险实验、本地原型与正式对外运行的要求分开。

本次任务完成取决于用户约定的成果。只有实际进入责任移交、退场或停运时，才使用生命周期手册相应检查：接手人能运行、未决风险有归属、必要权限已转移或关闭。没有交接证据不能称“已移交”；没有要求移交的持续项目，不因此无法结束一次阶段交付。
