# AI 产品经理分析知识底座

本文件用于支持 AI 产品的方案分析、设计、评估和复盘。目标是达到产品经理级理解：能看懂方案、判断适用性、识别风险、设计流程、定义指标并与研发沟通；不要求掌握复杂数学推导、从零训练模型或完成编程实操。

## 一、七个大节

### 1. AI、机器学习与深度学习

- 人工智能（AI）是让计算机完成识别、理解、预测、决策或生成等智能任务的技术和系统。
- 机器学习（ML）是让计算机通过数据学习规律，而不是完全依赖人工编写规则的方法。
- 深度学习是使用多层神经网络处理复杂数据的机器学习方法。
- 数据是用于学习、分析或判断的材料；特征是帮助模型判断的属性；标签是样本对应的正确结果。
- 训练是模型从样本中学习并调整参数的过程；推理是训练完成后处理新输入并产生结果的过程。
- 训练集用于学习，验证集用于调整方案，测试集用于检验新数据表现。
- 过拟合是模型在训练数据上表现很好、在新数据上表现变差；泛化是把学到的规律应用到新数据上的能力。
- 数据泄露会让测试信息意外进入训练过程，造成评估结果虚高。
- 规则系统适合条件明确、结果必须稳定且可解释的任务；机器学习适合规律复杂、有足够数据并能持续评估的任务。

产品判断重点：数据是否可靠、标签是否正确、测试集是否代表真实场景、错误代价是否可接受，以及是否需要规则或人工兜底。

### 2. 神经网络与 Transformer

- 神经网络通过输入层、隐藏层和输出层逐层处理数据并学习规律。
- 参数是训练中会被调整的内部数值；权重表示输入因素的重要程度；偏置帮助调整整体判断起点；激活函数决定信息是否继续传递。
- 深度学习能够自动提取复杂特征，并形成向量表示；向量表示是用一组数字表达对象特征和关系的方式。
- Transformer 是适合处理序列信息的神经网络架构。
- 注意力机制让模型动态判断哪些信息更重要；自注意力用于计算同一段输入内部不同位置之间的关系。
- 位置编码向模型提供词语或内容的顺序信息。
- 编码器主要把输入转换为内部表示；解码器主要根据已有信息生成输出；实际模型可以使用编码器、解码器或两者组合。
- Transformer 能改善长距离关系、多轮上下文和并行处理，但注意力机制不是事实核验，也不等于搜索或业务规则。

产品判断重点：区分模型结构、训练数据、知识来源和业务流程；不要因为结构先进就假设产品一定可靠。

### 3. 大语言模型、Token 与上下文

- 大语言模型（LLM）是使用大量文本训练、能够理解和生成语言的模型。
- 预训练让模型学习通用语言规律和知识关联；指令微调让模型更会按照具体要求完成任务；对齐让模型更符合人类意图、安全规范和产品要求。
- 模型生成的是基于上下文的语言结果，不等于经过事实核验的答案。
- 幻觉是模型生成看似合理但没有事实依据的内容。原因包括缺少资料、知识过期、问题含糊、资料冲突或产品强迫模型回答。
- Token 是模型处理文字时使用的基本单位，不完全等于汉字、词或英文单词。
- 上下文是当前可参考的指令、问题、历史消息、工具结果和资料；上下文窗口是模型一次能够处理的信息总量上限。
- 截断是输入过长时删除部分内容；压缩是把长内容改写成更短摘要或结构化状态；污染是无关、错误、冲突或恶意内容影响当前回答。
- 上下文越长不一定越好。过长会增加成本和延迟，也可能让关键内容被噪声淹没。
- 模型选择要综合任务复杂度、业务风险、输入规模、准确性、速度和成本；不能所有任务都使用最强模型。

产品判断重点：高风险问题要允许拒答、显示依据、核对版本并人工接管；不要把大语言模型当作自动更新的数据库。

### 4. Embedding、向量数据库与 RAG

- Embedding 是把文字、图片等内容转换成一组数字表示，以便比较语义相似度。
- 向量数据库用于保存向量及其文档、版本、部门、日期和权限等信息，并快速查找相似内容。
- RAG（检索增强生成）是先从外部资料中检索相关内容，再让模型根据资料生成回答的方法。RAG 不会永久改变模型参数。
- 文档切分把长文档拆成可检索片段；切分过大容易引入噪声，切分过小容易拆散条件、例外和适用范围。
- 元数据描述文档版本、生效日期、部门、地区和权限；权限过滤确保用户只能检索有权访问的资料。
- 召回是找出一批可能相关内容；关键词搜索依赖字面匹配；语义搜索依赖含义相似；混合搜索结合两者；重排是在候选资料中把最相关内容排前；生成才是模型组织最终答案。
- 引用应指向能支持结论的文档、章节、页码、原图区域或音视频时间戳。
- 常见失败包括召回遗漏、召回错误版本、模型误读、引用不支持结论和权限泄露。
- RAG 更适合经常更新的企业事实；微调更适合固定的任务习惯、格式和风格。微调不应单独承担持续变化的知识。

产品判断重点：把“没找到资料、找到错误资料、模型误读、权限错误、业务规则缺失”分开评估，不能只看最终回答是否流畅。

### 5. Agent

- Agent 是能够围绕目标进行多步规划、调用工具并执行任务的 AI 系统。
- 模型负责理解目标、组织步骤和生成结果；工具提供搜索、查询、计算、写入或通知能力；规划拆分目标；工作流约束顺序、条件和分支；记忆保存必要的对话或任务状态；人机协同处理高风险和例外。
- 工具调用是模型提出结构化请求，由系统验证参数和权限后实际执行外部工具的过程。
- 只读工具通常风险较低；写入工具会修改数据、提交审批或产生外部影响，需要更严格权限、确认和审计。
- 规划关注“下一步做什么”；工作流关注“什么条件下允许做、按什么规则做”。
- 记忆可以是当前上下文、任务状态、用户长期信息或业务知识。记忆越多不一定越好，错误记忆会持续污染后续任务。
- 高风险节点应设置人工确认；异常流程要处理超时、重复提交、权限不足、资料冲突、工具失败、循环和中断。
- 审计记录用户目标、资料来源、工具调用、权限判断、人工确认和最终结果。
- Agent 可以调用 RAG，也可以使用微调模型；它不会自动获得最新知识、业务权限或稳定的执行能力。

产品判断重点：固定规则优先用规则和工作流；多步骤、需要工具且可定义权限和兜底的任务才适合 Agent。

### 6. 多模态

- 多模态 AI 能处理两种或以上信息形式，如文本、图片、语音和视频。
- 图片理解可以识别物体、场景、文字、图表和布局；OCR（光学字符识别）只负责把图片中的文字转成可处理文本，不等于语义理解或业务判断。
- 语音识别把讲话转成文字；语音合成把文字转成声音。口音、噪声、数字和专业术语会影响结果。
- 视频理解通常结合音频、转写、字幕、关键帧和时间戳；关键帧是代表视频某个时间点的画面。
- 多模态系统可以先把图片和语音转换成文字，也可以直接交给多模态模型，或由多个模型协同处理。
- 多模态资料可以进入 RAG，但要保留原始图片、音频、视频、表格结构和可定位的引用信息。
- 常见错误包括识别错误、表格结构错误、语义误解、模态关联错误、版本错误和引用错误。
- 人脸、身份证、银行卡、会议声音和办公背景可能包含敏感信息；应考虑脱敏、保存期限、删除、权限和人工核验。

产品判断重点：使用“识别正确 → 结构完整 → 语义理解 → 资料匹配 → 业务判断 → 人工确认”的分层质量链路。

### 7. 成本、延迟、准确性与模型边界

- AI 成本包括模型输入输出、调用次数、检索、OCR、Embedding、向量库、工具、存储、人工审核、重试和错误造成的业务损失。
- 延迟包括上传、解析、检索、模型开始生成和完整生成时间；首字节延迟是看到第一部分输出前的等待，完整响应时间是全部结果完成的时间。
- 缓存复用已计算结果以降低成本和延迟，但必须考虑版本、权限、个性化条件和缓存失效。
- 流式输出可以改善等待感受，但不必然减少总耗时、Token 成本或错误。
- 限流限制单位时间请求量，保护系统和预算；并发是同一时间处理中的请求数量。
- 降级是在压力、故障或成本过高时使用更便宜的模型、较短输出、排队、检索片段或人工服务维持核心功能。高风险场景不能无提示地跳过引用和确认。
- 准确性不只包括答案正确，还包括资料版本正确、引用支持结论、合理拒答、权限合法和用户真正完成任务。
- 模型适合总结、分类、改写、提取和根据资料组织回答；不应单独承担无依据事实、最终财务法律决定、支付删除和绝对一致性的规则判断。
- 单位经济性分析的是“完成一次有效业务结果需要多少成本，以及该结果带来多少价值”，而不是单次 API 调用价格。

产品判断重点：用准确性、成本、延迟、安全和业务价值共同决策，不把调用量或生成量当成核心价值。

## 典型参考案例：企业知识库问答

企业知识库问答可作为分析技术链路和风险边界的参考案例，但真实项目应以项目自身的用户、资料、权限和业务流程为准。

标准判断链：

```text
用户问题
→ 身份和权限检查
→ 识别问题与必要条件
→ 检索有效版本资料
→ 召回和重排
→ 模型根据资料回答
→ 显示引用与不确定性
→ 高风险问题人工确认
→ 记录审计结果
```

必须覆盖的错误类型：资料过期、版本冲突、切分导致条件分离、召回遗漏、模型幻觉、引用不匹配、权限泄露、工具超时、重复提交、缓存失效、成本过高和高峰期延迟。

评估时至少区分：问题理解、资料召回、版本和权限、答案正确性、引用一致性、合理拒答、人工转接、严重错误率、响应时间、每个有效解决问题的成本。

## 全量分析完成标准

一次完整分析至少应能回答：

1. 用户问题和业务目标是什么，为什么需要或不需要 AI？
2. 数据、知识、模型、检索、工具、权限和人工分别负责什么？
3. 正常流程、失败流程、高风险流程和人工接管如何运行？
4. 如何评估理解、召回、生成、引用、拒答、安全、速度、成本和业务结果？
5. 模型和系统的能力边界是什么，哪些结论仍需验证或用户决策？

如果项目涉及某一技术模块，使用对应章节的完整检查项；如果项目不涉及某模块，明确记录“不适用”及原因，而不是假设它不存在。
